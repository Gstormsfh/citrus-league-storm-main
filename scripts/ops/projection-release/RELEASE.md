## Compatibility and rollback

[Actual Build 18 archive evidence](../../../docs/audits/build18-cutover-compatibility-20260912.md) establishes that its ROS/daily/dashboard requests and raw fields remain readable. New unconditional counts are not proven double-weighted by those archived branches. However, Build 18 still counts returned rows as appearances in some views, uses stored default points/fallbacks in others, and can retain a dashboard snapshot for the session. It cannot gain the new league-readiness, refresh or missing/zero handling from a server deploy. A fresh launch is necessary even to inspect newly fetched values. Corrected web and Build 19 are required for the full behavior; unsupported compatibility forecast categories such as plus/minus remain unavailable on corrected readers.

- **Before activation:** a failed migration transaction rolls back; installed empty canonical schema can remain while the prior API/web versions are restored. Legacy wrappers keep their old path. Scoring capture/repair/rescore is a single transaction; failure must not commit partial totals.
- **Failed activation or refresh:** the tested database transaction preserves the prior complete run/outputs. Failure health is explicit. No operator needs to delete immutable run history to recover.
- **Application rollback:** route Cloud Run traffic back to the freshly pinned prior revision and restore the pinned prior Hosting release. Observed baseline was `citrus-api-00310-q6p` / `6aef8ab7d5f4657245284377b53acbc915dc6d82`, but re-read before release. The exact traffic command is `gcloud run services update-traffic citrus-api --project=citrus-fantasy-prod --region=us-central1 --to-revisions="$CITRUS_PRIOR_API_REVISION=100"`. This operational command has not been run against production here. Retain the repaired scoring trigger, normalized rules, corrected totals and lines: the prior API already uses the same effective-rule scoring RPCs and unchanged result shapes. See the scoring companion README for the compatibility evidence and separate data-incident boundary.
- **After a committed source switch:** prefer a previously validated canonical run with expected-active CAS, only if its remaining calendar is still valid. On a first-ever switch there is no prior canonical run: the recovery transaction must compare the active revision, remove only that active pointer, and restore the pre-cutover ROS/future-daily snapshots before reverting readers; retain all immutable history. Do not narrow numeric columns or blindly reactivate an old calendar. This committed recovery is distinct from the completed transaction-rollback proof and needs the exact fresh snapshot in the release record.
- **Cache quarantine:** inverse rename is tested on the actual 1,461-row backup and preserves the same object/data/security. Restore immediately on a demonstrated caller failure. Keep the backup and agree an observation period before any later deletion proposal.

Local evidence: full-schema model/refresh/RLS/failure checks; actual-source test-copy activation of 674 ROS / 56,616 daily rows with all 12 exported categories, expected workload, independent default scoring and revision equality; complete rollback fingerprints; actual cache restore/rename/inverse. These prove the named local operations, not production traffic rollback, installed-device behavior or every external host caller.

The database boundary protects active outputs even if an obsolete external invocation still runs. `nightly_projection_batch.py` and `run_daily_projections.py` catch/log projection write failures; neither invokes raw NHL-stat ingestion in this chain. The nightly path still calls the ROS RPC and proceeds to derived difficulty when that succeeds. Optional directory/talent updates in the manual daily path run before projection writes. An obsolete caller may waste work and log failures until its actual invocation is retired, but it cannot silently replace authoritative active rows. Do not disable guessed jobs; cron 31/34 remain the supported refresh entrypoints. Cache quarantine still requires its separate external-reader check.
