# ⚠️ STEP 0 — READ THIS BEFORE YOU RUN ANY OF THEM

**None of the deploys below fixes the biggest problem.** Overnight I found that **a completed v2 draft produces no roster** — inbox E142. The draft records every pick perfectly and then nothing turns those picks into teams, so the roster page reads *"Empty Roster… head to the draft room to start drafting."* On staging, **1,177 of 1,188 teams with v2 picks have zero roster rows.**

**All three below are still worth doing** — the goalie board and the six client fixes are all real. **But running them does not make Aug 20 safe on its own.** The roster fix needs a migration plus a call site in the engine's completion path, and I deliberately did not write it into the tree: it is the highest-stakes change on the board and it needed you awake.

**What to do with it:**

1. Read `docs/PROPOSED_roster_sync_v2.sql` — the function is written, reviewed against the v1 original, and comes with a scoped backfill (dry run first) and the two non-SQL steps.
2. Decide who implements it — this session or the other one — and start it before anything else.
3. **Do not run the migration from this sheet.** It is a proposal, not a deploy step. It wants a review, a migration file, and your normal DB path.
4. **After you apply it, verify it actually landed.** `PROPOSED_roster_sync_v2.sql` now ends with two queries — one confirms the live function body in `pg_proc` reads `draft_picks_v2`, the other counts `roster_assignments` (expect rounds × teams). I found one migration on staging recorded as applied whose live function is not what the migration defines (inbox E155). One data point on a dead function, so not evidence of a broken pipeline — but this is the fix everything else waits on, and checking costs one query.

**Everything downstream of it heals on its own** once `roster_assignments` is populated — default lineups build themselves from it (E144). The blast radius is exactly one table.

# DEPLOY 1 — THE ENGINE. Still do this first; it is the goalie board.

**What it ships:** E117 + E118 — the autopick fix. Without it the engine drafts **five goalies in the first fourteen picks, including a four-game callup at #10** (measured on staging last night, inbox E125). Any seat whose clock expires on Aug 20 gets picked from that list.

**The one invariant that has bitten before:** build with **`-f server/Dockerfile.draft-engine`**. Building with the root `server/Dockerfile` puts the API server in the engine's slot — everything looks green, health returns 200, and no draft works. That was strike #2, a 13-minute outage on 2026-07-27.

```powershell
# ── 1. Push code ────────────────────────────────────────────────────
cd C:\Users\garre\Documents\citrus-league-storm-phase45

# Show what you're on first — this worktree should be on
# phase-4-5-implementation, but confirm rather than trust me.
git status -sb | Select-Object -First 1

# Push the current branch to whatever it already tracks. Deliberately
# NOT `git push origin <branch>` — the docs disagree about the branch
# name (18 references to phase-4-5-implementation, 6 to master) and I
# can't run git from here to settle it. This form is correct either way.
git push

# ── 2. Capture the SHAs ─────────────────────────────────────────────
$commitSha = git rev-parse --short HEAD
$fullSha   = git rev-parse HEAD
Write-Host "short=$commitSha  full=$fullSha"

# ── 3. Build the ENGINE image (note the -f — §15.11) ────────────────
$imageTag = "northamerica-northeast1-docker.pkg.dev/citrus-fantasy-staging/citrus-draft-engine/draft-engine:$commitSha-draft"
docker build -f server/Dockerfile.draft-engine -t $imageTag .

# ── 4. Push it ──────────────────────────────────────────────────────
docker push $imageTag

# ── 5. Capture the digest ───────────────────────────────────────────
$imageSha = (docker inspect --format='{{index .RepoDigests 0}}' $imageTag) -replace '^.*@',''
Write-Host "digest=$imageSha"

# ── 6. Set VM metadata — KEEP THE QUOTES (§15.12) ───────────────────
gcloud compute instances add-metadata citrus-draft-engine-staging `
  --zone=northamerica-northeast1-a `
  --project=citrus-fantasy-staging `
  --metadata="image-tag=$commitSha-draft,commit-sha=$fullSha,image-sha=$imageSha"

# ── 7. Trigger the redeploy ─────────────────────────────────────────
gcloud compute ssh citrus-draft-engine-staging `
  --zone=northamerica-northeast1-a `
  --project=citrus-fantasy-staging `
  --command="sudo google_metadata_script_runner startup"

# ── 8. Read the boot log ────────────────────────────────────────────
gcloud compute ssh citrus-draft-engine-staging `
  --zone=northamerica-northeast1-a `
  --project=citrus-fantasy-staging `
  --command="sudo docker logs citrus-draft-engine 2>&1 | grep -E 'deployment.fingerprint|event_subscription|hono.listening|uws.listening|watchdog_started|boot_scan' | tail -25"
```

### What step 8 must show

| line | meaning |
|---|---|
| `deployment.fingerprint` | **the `imageSha` must match step 5's digest** — this is how you know the right image is running |
| `hono.listening` | port 3001 up |
| `uws.listening` | port 3002 up — **this is the one the API-Dockerfile mistake kills** |
| `event_subscription.started` | LISTEN/NOTIFY connected |
| `event_subscription.self_test_succeeded` | round-trip proven |
| `event_subscription.watchdog_started` | liveness timer running |
| `registry.boot_scan_started` / `registry.boot_scan_complete` | the boot scan ran |

### ⭐ The free proof you get on this deploy — read it

I left a rig league armed on staging (`ada00015-…-01`, `in_progress`, 0 picks, 24-hour clock) **specifically so this restart proves the boot-scan resume path.**

**In `registry.boot_scan_complete`, look for `resumed` greater than 0.** That is the one Slice-1 contract never yet proven in the field — the mechanism that carries a live draft across an engine restart on Aug 20. **Please paste that line back.** No `boot_scan_threw` / `boot_scan_query_failed` anywhere.

*(Do not join or start that league. It exists to be resumed.)*

### If a step fails

Stop. The startup script pulls the new image **before** touching the running container, so a failure anywhere leaves the current engine serving. Investigate before re-running. Rollback pins are in the runbook, §D5.
