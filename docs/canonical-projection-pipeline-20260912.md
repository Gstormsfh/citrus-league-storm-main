# Canonical projection publication contract and historical rehearsal

**Current operating entry point: [Source → screen map](../scripts/ops/projection-retirement/CUTOVER.md).** Source publication, runtime activation and later reader repairs have occurred. The map links the current release receipt and qualified consumer acceptance; this document describes the architecture and preserves the original pre-publication rehearsal evidence. Do not use historical blockers, release status or fixture results below as current serving status.

The original September12 rehearsal preceded source publication. At that stage the imported draft had publication blockers and no production write had occurred. Those statements describe that rehearsal only; later reviewed publication and plus/minus propagation supersede them. The published source and effective runtime remain separate identities, and code release does not itself refresh either.

Four canonical migrations introduce immutable versioned run payloads, player records and a per-season active pointer. Authenticated readers can see only active runs through RLS and security-invoker views. Staged/rejected versions are hidden. Only `service_role` can call these internal mutation RPCs:

- `canonical_stage_projection_run(p_payload jsonb) -> uuid`: preserves the supplied revision and all source/review metadata; identical retries reuse the run; a differing payload under the same revision fails.
- `canonical_validate_projection_run(p_run_id uuid) -> jsonb`: returns `valid`, structured `errors`, and `checked_at` and stores that report.
- `canonical_activate_projection_run(p_run_id uuid, p_expected_revision text, p_expected_active_revision text DEFAULT NULL) -> jsonb`: revalidates, locks the season, switches the pointer and materializes both compatibility outputs in one transaction. Any failure rolls everything back. First publication requires no active revision; every later publication requires the exact currently active revision as a compare-and-swap guard, including internal nightly refreshes.
- `canonical_refresh_projection_run(p_season integer) -> jsonb`: creates a new revision from the same persisted policies and current existing model functions; retains the previous published snapshot on failure and records affirmative failure health.

`canonical_published_players` exposes `season, run_id, revision, player_id, payload`. `canonical_published_runs` exposes the active identity, full payload (including team notes), validation report, activation time and last-refresh time/status/error. It additionally exposes `source_run_id`, `source_revision`, and `source_payload`: the unchanged authoritative full-season input document, separate from the runtime-derived payload. Editors must export/edit `source_payload`, whose original Python-compatible revision and full-season count basis survive every refresh; the runtime PostgreSQL-JSONB digest is not an editable source-file hash. The editor/operator must separately record the active runtime revision and supply it to activation CAS. Nightly players remain derived from this one persisted policy source, not a second manually editable truth. ROS and daily compatibility rows carry `projection_run_id` and `projection_revision`; readers must match these stamps before attaching canonical context. The context service and dashboard enforce this attachment boundary. The serving baseline does not uniformly compare active revision across all direct ROS/daily response pages; see the current map for the focused review of that boundary.

Validation recomputes current directory coverage, scheduled team coverage and actual schedule budgets, raw count/rate/exposure identity, full-team crease conservation, remaining exposure bounds and aggregate skater capacity. It rejects imported blockers, incomplete review, missing source metadata, and unresolved or cross-team required lineup IDs. Auditable nonselected profiles may remain unavailable; optional depth requires both an optional source label and structured evidence, and cannot override an active label. An assumed lineup is allowed; this is not a claim of confirmed opening-night deployment. A team differing from the directory requires explicit `team_assignment: {reviewed: true, evidence: "..."}`. The service-role caller remains responsible for source authenticity and verifying the offline canonical SHA-256; SQL detects revision collisions but does not reproduce Python float/JSON serialization.

Initial activation preserves imported rates, counts and exposure, including intentional 83-game and injury overrides. Rates-only rows remain in the canonical record and are excluded from count outputs. Nightly refresh uses `project_ros` and `project_rookies` rather than choosing a different xG model. MODEL/DEFAULT policies refresh their model/cohort rates; MANUAL preserves explicit rates. Full-season goalie allocations remain crease weights and are distributed across the remaining schedule, preserving zero and fractional starts. Manual skater exposure becomes `min(team games remaining, max(0, season override − actual regular-season games))`. Actual participation uses positive official/calculated TOI on regular-season game IDs before the current date; absent skater statistics after a team has played block refresh instead of inventing zero. Goalie actual GP is counted from positive goalie_gp when supported; otherwise it remains null while future crease weights remain independently known. This conservative gate can require an explicit participation/ingestion resolution for players who did not dress.

Daily canonical rows are unconditional expected counts, marked `canonical_expected_volume_v1`. Their expected games/starts and each category sum to the ROS output across the remaining calendar. No additional home/B2B, roster, injury, or start multiplier is applied. Existing conditional rows remain unchanged; backend adapters add their units separately. These are forecasts of workload, not confirmed starts. No confirmed-starter feed is introduced. Day boundaries follow the database's `current_date`; intraday consumers still apply existing game-state/fraction logic.

The ROS compatibility table has a player-only primary key and remains a single-season cache, like its prior writer. Canonical history and published views retain season identity separately. Daily historical rows remain historical; refreshed future rows share the new run. Numeric typmods on projected exposure/categories are widened to avoid rounding away fractional starts or accumulating category drift. Production read-only dependency inspection found no dependent views on either projection table, and no live typed `get_ros_projections` function; a compatibility block updates that older function if present while preserving execute grants.

The existing ROS cron entrypoint becomes the authoritative refresh/materialization path. The daily entrypoint reuses the active snapshot and cannot independently call the model. Without an active canonical run, both wrappers call their original functions. A failed refresh keeps previous values and exposes `last_refresh_status='failed'` plus error text; daily materialization refuses to redistribute a stale crease across a shorter horizon. Consumers can distinguish staleness from a new successful revision. External alert wiring is not implemented here.

Security/scoring review exceptions are explicit: this is an internal service-role writer, so it has no user-supplied user/team mutation or `auth.uid()` flow. Immutable runs and stored validation/health provide its database audit trail; an application `AuditService` event is not invoked by SQL. SQL cannot call the TypeScript `ScoringCalculator`: its single default scorer is generated from the same scoring JSON and parity-tested. Custom league scoring remains in `ScoringCalculator`. These are deliberate boundaries, not claims that every skill checklist item is literally satisfied.

The final write-boundary migration (`20260912073540`) gives the existing fixed-body materializer a dedicated NOLOGIN owner role; no application/service membership, SET ROLE permission, schema CREATE permission or extra data store is introduced. The role has only its required table/function privileges and explicit RLS policies. An invoker trigger permits its canonical output writes and rejects every other active-season ROS or future daily insert/update/upsert/delete, even when obsolete callers preserve valid revision stamps and calculation-method fields. Active-output TRUNCATE is rejected too. With no active run, ordinary READ COMMITTED legacy writes remain allowed; historical daily repairs remain allowed.

The trigger uses the same seasonal advisory lock as activation. Noncanonical ROS/future writes under REPEATABLE READ or SERIALIZABLE fail explicitly with a request to retry at READ COMMITTED, preventing a pre-activation snapshot from bypassing the active-pointer check. A tuple/advisory lock inversion can still make PostgreSQL abort one transaction as a deadlock victim; the entire transaction must roll back and retry through the correct writer. No partial forecast writes are intentionally accepted. This is an application-writer boundary, not protection against a database administrator who can change owners, grants, pointers or triggers. The Supabase `postgres` role was inspected read-only: CREATEROLE true, SUPERUSER false; ownership transfer was rehearsed under those local-image permissions.

`docs/verification/canonical-write-boundary-20260912.json` records direct-write rejection, valid-stamp retention, GUC and SET ROLE rejection, isolation handling, historical/no-active exceptions and concurrent lock behavior. The five-migration full-schema and actual-source test-copy reports were regenerated with this guard installed.
